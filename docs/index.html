>_ZDBVIEW

One binary for both halves of the cache. A SQLite database gets full generic CRUD — browse tables, edit any cell, insert and delete rows, run raw SQL — because SQLite is self-describing. An rkyv archive gets a structural inspector — info, embedded strings, hex — because rkyv is not. Which one you get is decided by the file's header bytes, never by its name.

Quickstart

# build from source
git clone https://github.com/MenkeTechnologies/zdbview
cd zdbview && cargo build --release

# open a database — kind is detected from the header magic
zdbview app.sqlite               # SQLite  → full CRUD
zdbview ~/.cache/zshrs/plugins.db  # rkyv   → structural inspection (despite the .db name)

# force a backend
zdbview --sqlite file
zdbview --rkyv   file

# no argument → pick from recently opened files
zdbview

File type detection

The first 16 bytes are compared against the SQLite header magic SQLite format 3\0. When a full header is readable the magic decides alone — its absence means the file opens in the binary inspector, whatever the extension says.

SituationResult
Header readable, magic presentSQLite backend
Header readable, magic absentrkyv / binary inspector — extension ignored
File shorter than 16 bytesExtension tie-breaker: .db / .sqlite / .sqlite3 → SQLite, else inspector
--sqlite / --rkyvShort-circuits both rules
Magic present but SQLite refuses the fileFalls back to the inspector instead of failing

Trusting the magic over the name is the whole point: rkyv cache shards are routinely written under a .db name, and an extension-first reader hands those to SQLite, which then reports a corrupt database for a perfectly valid archive.

SQLite — generic CRUD

The left pane lists tables and views from sqlite_master; the right pane shows one 500-row page of the selection. Every edit and delete addresses its row by rowid, selected alongside the real columns as SELECT rowid, * FROM <table> — which is what makes the CRUD generic: no schema knowledge, no primary-key guessing, no per-database configuration.

KeyOperation
eEdit the selected cell. Enter runs UPDATE "<table>" SET "<col>" = ?1 WHERE rowid = ?2 with the text bound as a parameter, then reloads the page.
aInsert one row with INSERT INTO <table> DEFAULT VALUES.
dDelete the selected row after a y confirmation.
:Run an arbitrary SQL statement; the affected-row count lands in the status line and the page reloads.

Identifiers are double-quoted with internal quotes doubled, so table and column names containing spaces or keywords work. A WITHOUT ROWID table has no generic row handle, so its rows are listed read-only. Values display by type: integers and reals verbatim, text as UTF-8, NULL as NULL, blobs as <blob N bytes>.

rkyv — structural inspection

An rkyv archive is a memory image of a Rust value plus a root pointer. The format stores no field names, no type tags and no embedded schema — the originating Rust type is the schema. Without it, no reader can know whether eight bytes are a u64, two u32s, or a relative pointer, so zdbview shows what is recoverable from the bytes rather than pretending to know the fields.

ViewShows
1 — InfoPath, byte size, and how many string runs were extracted.
2 — StringsEvery run of ≥ 4 printable ASCII bytes with its hex offset — in practice the keys, interned identifiers and string fields, in archive order.
3 — Hexxxd-style dump: 16 bytes per line as offset  hex  |ascii|.

Typed, field-name CRUD over an archive needs a supplied schema descriptor and is deliberately out of scope for this release.

Search

/ takes a plain substring (not a regex); n and N then walk the matches. What is scanned depends on the mode and, in SQLite, on which pane has focus.

ModeScanned
SQLite — tablesTable names, case-insensitive, wrapping
SQLite — rowsEvery column of the loaded page, case-insensitive, wrapping. Page-local: page first, or use : with a WHERE clause
rkyv — StringsThe extracted runs, case-insensitive, wrapping
rkyv — HexRaw bytes, case-sensitive, does not wrap; the view scrolls to the hit and the offset is reported
PickerRecorded file paths, case-insensitive, wrapping

Recent files

Every successful open is recorded to $XDG_CACHE_HOME/zdbview/recent (or ~/.cache/zdbview/recent), one tab-separated line per entry: unix-seconds kind absolute-path. Paths are canonicalized, so the same file reached by different relative paths or symlinks dedupes to a single entry that moves back to the front on re-open. The list is capped at 50 and written via temp-file-plus-rename, so a concurrent reader never sees a half-written list. The recorded kind is the one actually used — a .db file that turned out to be an archive is remembered as rkyv.
